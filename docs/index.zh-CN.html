Spring Boot Workflows 把 Claude Code 从一个被动的聊天助手，变成一位结构化的工程伙伴： 它会遵循规格、与你一起头脑风暴、逐阶段编写代码、运行质量门禁并创建 PR —— 而且横跨多个会话，全程不丢失上下文。

/plugin install spring-boot-workflows
问题所在

Claude Code 很强大，但缺乏结构

没有工作流时，每次对话都要从零开始。Claude 不记得你的流程、你的约定，也不记得你上次做到哪儿了。

💥

流程没有记忆

每一个会话你都要反复解释同样的架构决策、编码约定和 git 流程。上下文一重置，Claude 就把一切都忘了。

💡

持久化的工作流状态

Spring Boot Workflows 把决策存进 YAML 状态文件和上下文快照。几天之后恢复任何工作流，上下文依然完整。

💥

质量忽高忽低

有时 Claude 写的代码很棒，有时它会跳过测试、无视约定，或者不做评审就创建 PR。毫无保证。

💡

每个边界都有质量门禁

每个 PR 之前强制运行评审清单。实现之前加载语言专用的编码规则。只对实际改动的文件做聚焦检查。

💥

复杂任务没有章法

要开发一个功能？Claude 直接跳去写代码。没有规格、没有计划、没有备选方案的头脑风暴。你得到的只是它想到的第一种做法。

💡

分阶段执行，逐段确认

收集需求 → 编写规格 → 头脑风暴方案 → 制定计划 → 实现 → 测试 → 评审 → PR。每个阶段都需要你批准。

💥

所有任务一视同仁

改 3 行配置和开发一个大型功能得到同样的对待：「这是代码。」完全不区分复杂度与风险等级。

💡

24 个专用工作流

紧急修复快速而克制，新功能严谨而完整，重构有行为契约兜底。每个工作流都为它的任务量身打造。

它做什么

一个面向 Claude Code 的工作流引擎

它把结构化的技能、规则与清单装进你的项目，引导 Claude 以有纪律的方式做 Java 与 Spring Boot 开发

技能（Skills）：一步一步的指令

每个工作流都是一个技能 —— 一个 markdown 文件，里面是 Claude 要遵循的、 逐阶段的详细指令。当你输入 /spring-boot-workflows:new-feature 时，Claude 会读取该技能， 按顺序执行每个阶段，同时写出产出文档并更新状态。

  • 24 个技能，覆盖完整的开发生命周期
  • 27 个 Spring Boot 领域技能（JPA、REST、安全、Flyway、测试），由 spring-context 路由按需加载
  • 每个技能含 3-8 个阶段，并设有审批门
  • 阶段产物以 markdown 持久化，便于恢复上下文
  • 技能可组合 —— new-feature 会委派给 brainstorm
  • 可用 /spring-boot-workflows:compose-skill 创建你自己的技能
1# 你输入：
2/spring-boot-workflows:new-feature user-authentication
3
4# Claude 依次执行 8 个阶段：
5阶段 1: GATHER — 收集需求
6阶段 2: SPEC — 编写正式规格
7阶段 3: BRAINSTORM — 与你一起探索方案
8阶段 4: PLAN — 制定分阶段实现计划
9阶段 5: BRANCH — 创建 git 分支
10阶段 6: IMPLEMENT — 逐阶段实现
11阶段 7: TEST — 验证正确性
12质量门禁 — 检查 37 项通用 + 45 项 Spring 条目
13阶段 8: PR — 推送并创建拉取请求

规则（Rules）：编码自动巡航

两份 DO/DON'T 规则文件会在 Claude 写任何 Java 代码之前加载： rules/java.md 管语言，rules/spring-boot.md 管框架。 这些不是建议，而是指令。「Boot 4 里永远别用 @MockBean。」 「永远别用字段注入。」Claude 会自动遵守，无需你反复交代。

  • 2 份规则文件：java.md 与 spring-boot.md
  • 依据 project.type 自动加载 —— spring-boot 会同时加载两份
  • 团队约定叠加在语言规则之上
  • Boot 3 与 Boot 4 的差异靠检测得出，绝不猜测
# 插件内置 rules/java.md
## record 与 class
DO： 用 record 表示 DTO、请求/响应载荷、值对象
DON'T： 用 record 表示需要变更的 JPA 实体
## 空安全
DO： 在 package-info.java 中用 @NullMarked（JSpecify）
DON'T： 给每个参数都显式标注非空
## 异常
DO： 包装异常时保留原始 cause
DON'T： 捕获 Exception 后返回 null

评审清单（Review Checklists）：可信赖的质量

每个 PR 之前，Claude 会对照按严重级别划分的清单做一次自评审。 严重级别的条目（硬编码密钥、SQL 注入、缺失鉴权）必须通过。 聚焦门禁只会检查与真正改动过的文件相关的条目。

  • 通用清单 37 项（架构、安全、性能、测试）
  • Java 清单额外 44 项，Spring Boot 清单额外 45 项
  • 严重级别：Critical 阻止合并，High 应当修复，Medium/Low 为提示性建议
  • 团队清单用于领域特定标准
  • 聚焦门禁：安全相关文件跑全部安全检查，UI 文件跑 XSS 检查
# PR 前的质量门禁

[高]     遵循项目既有模式 PASS
[高]     所有错误均已处理 PASS
[高]     存在对应测试 PASS
[中]   无 N+1 查询 PASS
[中]   函数长度 <40 行 PASS

状态（State）：永远不会找不到进度

Spring Boot Workflows 采用三层持久化模型，因此你可以随时关掉终端， 第二天回来，从上次的位置精确继续。状态文件使用 YAML frontmatter 以便可靠解析。上下文快照在每次阶段边界记录关键决策。

  • 第 1 层：状态文件 —— 当前阶段、分支、重试次数、阶段历史
  • 第 2 层：阶段产物 + Context 小节 —— 每个阶段的完整细节，关键决策写入状态文件
  • 第 3 层：Git + 知识图谱 —— 提交、分支，以及跨工作流的决策学习

workflow: new-feature

每个工作流都是一台状态机

各阶段顺序执行，并在边界处做质量检查。错误恢复机制内建其中。

/spring-boot-workflows:start → GATHER → SPEC → BRAINSTORM → PLAN → BRANCH
IMPLEMENT → TEST → 质量门禁 → PR → CHAIN → 下一步
■ 思考与决策 ■ 构建与验证 ■ 质量门禁 ■ 交付与串联
24 个工作流技能

为每种任务提供恰当的流程

为各种开发场景量身打造的工作流，从紧急热修复到完整的功能开发

⚙️

新功能（New Feature）

从需求到 PR 合并的完整功能生命周期
它做什么：收集需求（来自 Jira、Figma，或交互式提问），编写正式规格，与你一起头脑风暴实现方案，制定按架构分层排序的分阶段计划，逐个提交地实现并做构建检查，运行测试，通过质量门禁之后创建 PR。
/spring-boot-workflows:new-feature <name>
🔥

紧急修复（Hotfix）

生产环境紧急修复，为速度而优化
它做什么：从堆栈跟踪、Crashlytics 或日志文件出发诊断崩溃，定位根因，施加绝对最小的修复（理想 1-5 行，超过 15 行会警告），编写一个在没有该修复时必然失败的强制回归测试，向生产分支提 PR，并给出回移到开发分支的 cherry-pick 方案。
/spring-boot-workflows:hotfix <description>
🔄

重构（Refactor）

带行为保证的代码重组
它做什么：绘制完整依赖图（入向 + 出向）。在动代码之前先记录行为契约。规划增量迁移，保证每一步都能编译并通过测试。采用并行弃用策略：新代码与旧代码并存，逐个迁移调用方，直到引用归零才删除旧代码。
/spring-boot-workflows:refactor <target>
🔎

代码评审（Code Review）

带行内评论的系统化 PR 评审
它做什么：拉取 PR diff，按架构分层对文件分类，完整阅读每个改动文件（而不只是 diff）。对照已加载的清单检查，用 4 个严重级别：Critical（阻断）、High、Medium、Low。生成带可执行修复建议的行内评论，并通过 GitHub API 提交。
/spring-boot-workflows:review <pr-number>
💡

头脑风暴（Brainstorm）

用结构化技法进行的交互式设计探索
它做什么：主导一场协作式对话（绝不单方面分析）。使用的技法包括：权衡矩阵、六顶思考帽、SCAMPER、逆向头脑风暴、约束映射。按复杂度分三个深度级别。按加权维度为选项打分。从知识图谱中调出相关的历史决策。你来决定 —— Claude 负责引导。
/spring-boot-workflows:brainstorm --topic "..."
🧪

测试生成（Test Generation）

覆盖率分析、分支映射、分类测试
它做什么：分析目标的公开 API，映射每一条代码分支（正常、错误、边界、状态、并发）。规划带标签的测试：[HAPPY] [ERROR] [EDGE] [STATE] [INTEGRATION]。按 Given/When/Then 命名编写测试。对照可配置的目标覆盖率检查（默认 90%）。报告缺口并说明原因。
/spring-boot-workflows:test <target>
🔨

扩展功能（Extend Feature）

在不破坏既有行为的前提下增加能力
它做什么：分析既有功能的代码，找出可以在不修改既有代码的情况下挂接新行为的扩展点。优先新增文件而非修改。保证：不改签名、不改测试断言、不改变行为。运行完整的兼容性验证。
/spring-boot-workflows:extend-feature <name>
⚡

CI 修复（CI Fix）

自动诊断并修复失败的 CI/CD 流水线
它做什么：通过 gh CLI 获取 CI 失败日志。分类：编译错误、测试失败、lint 违规、依赖问题、配置错误、超时，或不稳定的测试。按类别施加针对性修复。推送并监控重试结果。如果再次失败，最多循环 3 次，每轮重新诊断。
/spring-boot-workflows:ci-fix
🛠️

CI 生成（CI Setup）

为 GitHub Actions 与 Gitea Actions 生成 Maven CI 工作流
它做什么：检测平台、构建系统、Java 版本与质量工具，生成测试、覆盖率、静态分析与制品上传步骤；校验 GitHub/Gitea 的上下文命名空间与 Action URL 差异，并保证 Maven 缓存路径与实际本地仓库一致。
/spring-boot-workflows:ci-setup [--platform github|gitea]
🚢

迁移（Migrate）

依赖、API、架构、数据库
它做什么：任何改动之前先记录当前状态。评估迁移策略（一次性切换、增量、并行运行、绞杀者模式）。制定计划，确保每一步都能独立编译并通过测试。提供类型专属指导：依赖版本升级、API 版本替换、架构模式迁移、带可回滚迁移的数据库 schema 变更。
/spring-boot-workflows:migrate <type>
🚀

发布（Release）

变更日志、版本递增、分支、PR、标签
它做什么：从 git 历史生成变更日志，并按 conventional commit 类型分类。在正确的文件里检测并递增版本号（pom.xml、build.gradle、build.gradle.kts）。创建发布分支、带质量门禁地提 PR 到生产分支，并提供合并后的打标签命令。
/spring-boot-workflows:release <version>
🏠

新项目（New Project）

为项目初始化完整的 Claude Code 配置
它做什么：扫描 Maven/Gradle 构建文件，检测 Spring Boot 主版本与持久化技术栈，再从历史中提取 git 约定。生成 .workflows/config.yml 和 CLAUDE.md，内含构建命令、架构摘要与代码约定。搭好任务跟踪的脚手架，创建 .workflows/ 子目录，更新 .gitignore，并可生成 CI。对新项目而言它取代 /setup。
/spring-boot-workflows:new-project [--path <dir>]
📃

模板（Templates）

复用过去工作流中的规格与计划
它做什么：把已完成工作流的规格 + 计划保存为可复用模板，支持参数占位符。下次要构建类似功能时，/spring-boot-workflows:template use api-endpoint user-mgmt 会预填规格与计划，完全跳过 GATHER 和 SPEC 阶段。模板会记录使用次数。
/spring-boot-workflows:template save|list|use
新
🔧

技能编排（Skill Composer）

以交互方式构建自定义工作流技能
它做什么：询问这个技能做什么、有哪些阶段、每个阶段产出什么、是否需要头脑风暴、是否会创建 PR。生成一个结构规范的 SKILL.md，包含 YAML frontmatter、编排集成、阶段输出路径与错误处理。阶段相关的具体逻辑由你填充。
/spring-boot-workflows:compose-skill <name>
新
📊

度量（Metrics）

跟踪工作流速度、瓶颈与趋势
它做什么：读取遥测数据（每个阶段之后写入的 JSON lines）。展示完成率、平均耗时、瓶颈阶段，以及按工作流的细分统计。/metrics trends 会把最近 10 个工作流与此前 10 个做对比，查看速度变化与 REPLAN 频率。
/spring-boot-workflows:metrics [trends]
新
🔌

Git Flow

按项目约定进行分支、提交、PR、合并操作
它做什么：按配置的模式创建分支（feature/{name}、hotfix/{name}）。按你的格式校验提交信息（conventional、angular、simple）。按配置的基分支、评审人（GitHub）、标签与草稿模式创建 PR。按配置的策略合并（squash/merge/rebase）。对受保护分支发出警告。
/spring-boot-workflows:git-flow branch|commit|pr|merge
📚

学习（Learn）

捕获并复用成功的模式
它做什么：从已完成的工作流中提取可复用模式：架构决策、实现模式、测试策略、问题解决方式。以带标签的 markdown 存储。被使用 2 次以上的模式会被标记为「已验证」，并在未来的头脑风暴中自动浮现。
/spring-boot-workflows:learn capture|list|apply
🔍

诊断（Diagnose）

以假设验证进行系统化的缺陷排查
它做什么：复现缺陷，生成带证据的排序假设，然后用针对性测试或 git bisect 逐一排除。记录确认的根因，给出确切的文件、行号与影响范围 —— 但不做修复。随后交由 /hotfix 或 /new-feature 去修复。
/spring-boot-workflows:diagnose <symptom>
新
📏

范围评估（Scope）

动手之前先做复杂度预判
它做什么：扫描代码库找出受影响的文件，统计涉及的分层数量，检查是否存在破坏性变更。给出复杂度评级：Trivial（微不足道）、Small（小）、Medium（中）、Large（大）、Epic（史诗级）。推荐应使用哪个工作流，并为超大型任务给出具体的拆分建议与依赖顺序。
/spring-boot-workflows:scope <description>
新
📈

复盘（Retrospective）

分析工作流历史以改进流程
它做什么：读取遥测与工作流历史，找出做得好的地方（成功率高的流程）、问题（反复出现的 REPLAN 触发）与瓶颈（总是出岔子的阶段）。生成可执行的改进建议，并给出具体的配置改动。可自动应用已批准的配置更新。
/spring-boot-workflows:retrospective
新
🛡️

守卫（Guards）

针对凭据与危险操作的安全检查
它做什么：用 guards.yml 中可配置的阻断/警告模式扫描暂存文件。检测硬编码令牌（AKIA、sk-、ghp_、Bearer）、受保护路径违规，以及危险操作（rm -rf）。BLOCK 级别会直接阻止操作，WARN 级别只提示但允许通过。越权放行会留痕，便于审计。
/spring-boot-workflows:guards init|check|report
🔧

初始化（Setup）

让现有项目接入工作流体系
它做什么：检测构建系统（优先 wrapper）、Spring Boot 主版本、持久化技术栈，创建 .workflows/ 目录结构，由插件默认值 + 你的 userConfig 合成 .workflows/config.yml，并把工作流状态条目写进 .gitignore。--with-guards 可同时生成守卫配置。全新项目请改用 /new-project。
/spring-boot-workflows:setup [--with-guards]
🎮

入口（Start）

不确定用哪个？从这里开始
它做什么：先检查有没有活动工作流 —— 有就给你「恢复 / 暂停 / 放弃」三个选项；然后按 Build / Fix / Improve / Ship / Think / Meta 六组列出全部工作流，收集完参数后直接执行对应技能。它同时也是查看当前进度的入口。
/spring-boot-workflows:start
🔄

恢复（Resume）

跨会话接上被打断的工作流
它做什么：定位状态文件、解析并校验状态、加载 Context 小节里的关键决策与规格计划、汇报当前阶段与进度，然后从中断处精确继续。构建失败三次触发的 REPLAN 也可以从这里接上。
/spring-boot-workflows:resume
推荐路径

按你此刻的状态选技能

3
是新建还是改动？新建能力 → /new-feature；给既有功能加东西 → /extend-feature

强力特性

它与众不同的地方

不只是提示词 —— 而是一套内建智能的完整编排引擎

🔗 工作流串联

在 YAML 中配置工作流的自动接续。当 /spring-boot-workflows:new-feature 完成后，Claude 会建议 /spring-boot-workflows:review --self；热修复完成后，建议 /spring-boot-workflows:ci-fix。相关流程之间零手工交接。

📸 上下文快照

每个阶段之后，关键决策会追加到状态文件的 Context 小节（3-5 条要点）。当 Claude 的上下文窗口在长工作流中压缩旧消息时，它会重新加载 Context 小节，恢复此前的全部推理。「我都忘了阶段 2 我们决定了什么」这种事不会再发生。

⚡ 自适应深度

自动感知任务复杂度。改 1-2 个文件、不到 20 行的配置会跳过 SPEC 与 BRAINSTORM（微不足道）；超过 10 个文件、涉及架构改动的需求则强制进行多种技法的深度头脑风暴（复杂）。显式传 --depth trivial 会连 TEST 一起跳过，用 --depth full 可覆盖回完整流程。每个任务都得到恰到好处的流程。

🧠 知识图谱

每次工作流结束后，决策会被提取到 knowledge.jsonl。在未来的头脑风暴中，Claude 会主动提示：「上次你遇到类似的约束（离线优先），选择了事件溯源 —— 它成功了。」团队的集体记忆，被编码下来。

⚗ 并行执行提示

各阶段内相互独立的子步骤会被标记为可并行执行。Review 的 FETCH 阶段会并发发起 4 个 API 调用，而不是串行。正确性不变，完成更快。

🛠 18 条编排规则

适用于每个工作流的通用规则：状态初始化、阶段产物、跳过逻辑、质量门禁、构建检测、完成、暂停、错误恢复（REPLAN）、技能组合、检查点、遥测、试运行、串联、知识提取。这是驱动每个技能背后的引擎。
使用指南

如何使用这个插件

从安装到完成第一个功能 —— 以下是你将会经历的确切过程

安装插件

在 Claude Code 内运行以下命令。它会下载插件，并提示你配置 5 个选项。

# 在 Claude Code 内
/plugin marketplace add chinaares/spring-boot-workflows
/plugin install spring-boot-workflows

# 你会被问到：
# - 项目类型（spring-boot, java, generic）
# - 团队（spring 或 none）
# - 主分支名（默认：main）
# - 开发分支名（默认：develop）
# - 提交格式（conventional, angular, simple）
会发生什么：插件的技能、规则与清单会在该项目内的每一次 Claude Code 会话中，以 /spring-boot-workflows:* 命令的形式提供。

初始化你的项目

全新项目请运行 new-project —— 它会检测技术栈、git 约定与架构，然后写出配置、项目上下文文件和任务脚手架。

# 在 Claude Code 内 —— 新项目
/spring-boot-workflows:new-project

# 指定其他目录，或给一个兜底预设：
/spring-boot-workflows:new-project --path ../api-service

# 已有项目只需要补一份配置：
/spring-boot-workflows:setup
会发生什么：生成 .workflows/config.yml，其中填入检测到的项目设置（构建系统、语言、git 约定），外加 CLAUDE.md、tasks/ 与状态目录。生成之后你可以自行定制 config.yml。不要在 /new-project 之后再跑 /setup —— 两者都会重写配置，而 setup 那份会丢掉探测出的 PR 目标分支。

启动你的第一个工作流

用 /start 浏览全部可用工作流，或直接跳到某一个。

# 浏览可用工作流
/spring-boot-workflows:start

# 或直接进入某个工作流
/spring-boot-workflows:new-feature user-authentication
/spring-boot-workflows:hotfix null-crash-login
/spring-boot-workflows:review 42
/spring-boot-workflows:brainstorm --topic "caching strategy"
会发生什么：Claude 会在 .workflows/current-state.md 创建状态文件，显示进度指示，并开始第一个阶段。对 /new-feature 而言，它会以交互式收集需求开始。

逐个阶段推进

Claude 按顺序执行各阶段。有些阶段在继续之前会请求你的批准，另一些则自动推进。

# new-feature 工作流中的典型交互：

# GATHER：Claude 向你提问，了解功能需求
# SPEC：Claude 写出规格，问「是否批准？」
# BRAINSTORM：来回交互式地探索各种方案
# PLAN：Claude 制定实现计划，问「是否批准？」
# BRANCH：自动创建 git 分支
# IMPLEMENT：逐阶段实现，并做构建检查
# TEST：运行测试，报告覆盖率
# PR：运行质量门禁，创建拉取请求
你应该期待：每个阶段之后，Claude 会写出一个产物文件（例如 01-gather.md）并更新状态。一行进度提示会告诉你所处的阶段：✓GATHER ✓SPEC ▷BRAINSTORM ·PLAN ·IMPLEMENT ·TEST ·PR

暂停、恢复与恢复现场

你可以随时暂停，之后再恢复 —— 哪怕是几天后的新会话。

# 暂停当前工作流（随时说 "pause" 即可）
# Claude 会保存进度，并把状态文件重命名为 paused-<feature>.md

# 之后再恢复（下次会话时，Claude 会自动检测活动工作流）
/spring-boot-workflows:resume

# 如果构建失败 3 次以上，Claude 会触发 REPLAN
# 你审阅调整后的计划并批准，然后继续
你应该期待：恢复时，Claude 会校验分支、检查产物文件、加载 Context 小节（关键决策），并从中断处精确继续。当你启动 Claude Code 时，会话钩子会自动提醒你存在活动工作流。

检查质量并交付

每个 PR 之前，Claude 都会对照按严重级别划分的清单做一次自评审。

# 质量门禁在 PR 阶段自动运行
# Claude 加载通用 + 语言专用 + 团队清单
# 档位随改动规模伸缩：≤3 文件 Light · 4-15 文件 Standard · >15 文件 Full
# 逐项检查每个「严重/高」条目，并给出明确证据
# 在创建 PR 之前修复「严重/高」级别的问题

# 你也可以评审他人的 PR：
/spring-boot-workflows:review 42 --strict
你应该期待：创建的 PR 带有结构化的正文：摘要、按阶段组织的改动、测试结果，以及质量清单。严重问题会在 PR 创建之前被修复 —— 而不是之后。

持续学习与改进

工作流完成后，捕获模式并跟踪度量，以改进你的流程。

# 从上一个工作流中捕获模式
/spring-boot-workflows:learn capture

# 查看工作流度量
/spring-boot-workflows:metrics
/spring-boot-workflows:metrics trends

# 对近期工作流做一次复盘
/spring-boot-workflows:retrospective --last 10
你应该期待：学到的模式会在未来的头脑风暴中自动浮现。每完成一个工作流，知识图谱就会增长一分。度量会显示完成率、REPLAN 频率与瓶颈阶段。
小任务不必走全套仪式

用 --depth trivial 跳过 SPEC、BRAINSTORM 与 TEST，适用于简单改动。或者先用 /scope 判断是否真的需要完整工作流 —— 它给出的复杂度分档会直接告诉你该走哪条。

自动化审批门

在 /new-feature、/extend-feature、/refactor 或 /migrate 上使用 --auto 参数跳过交互式审批。当需求已经非常明确时很有用。

复用过去的工作

完成一次高质量的工作流后，运行 /template save api-endpoint。下次用 /template use api-endpoint user-mgmt 即可预填规格与计划，从 PLAN 阶段继续。

一切皆可定制

编辑 .workflows/config.yml，可以关闭新功能、扩展、重构、迁移工作流中的头脑风暴与测试阶段、修改 PR 基分支、设置计划阶段上限、配置合并策略，或设置工作流串联。
